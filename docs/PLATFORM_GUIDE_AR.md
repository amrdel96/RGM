# دليل منصة RGM للتشغيل والتعديل

هذا الدليل هو نقطة البداية لأي تعديل. اقرأ القسم المرتبط بالمطلوب فقط، ثم اطلب من Codex تعديل الملف المحدد وتشغيل الفحص المذكور. لا تعيد بناء المشروع أو تفحص كل الملفات عندما يكون التعديل محصورًا في صفحة أو ميزة واحدة.

## 1. ما الذي تعمل به المنصة فعليًا

المشروع تطبيق **Next.js 16 وReact وTypeScript**. النسخة الكاملة تعمل على خادم Node.js مع PostgreSQL، وSupabase Auth للحسابات، وCloudinary لملفات الماكينات. GitHub Pages يعرض نسخة واجهة ثابتة للمعاينة فقط؛ لا يستطيع تشغيل الحسابات أو API أو قاعدة البيانات.

| الجزء | الوضع في كود المنصة | مكان الإدارة |
|---|---|---|
| الموقع العام عربي وإنجليزي | مكتمل في تطبيق Next.js | المحتوى والإعدادات في Admin |
| كتالوج الماكينات والبحث | مكتمل، ولا تظهر إلا AVAILABLE أو RESERVED عند تفعيلها | Admin → Machines |
| صفحة منتج/ماكينة | مكتملة: معرض، مواصفات، سعر عند الطلب، استفسار وWhatsApp | Admin → Machines → machine |
| لوحة الإدارة | مكتملة بالصلاحيات ADMIN وSALES وMARKETING | `/admin` |
| الاستيراد CSV/XLSX | مكتمل | Admin → Bulk import |
| العملاء وتأكيد البريد | مكتمل في الكود، يحتاج Supabase مفعلًا | `/account` وSupabase Auth |
| النشرة البريدية | اشتراك بتأكيد مستقل موجود في الكود، يحتاج مزود بريد | تذييل الموقع وPostgreSQL |
| البريد وWhatsApp | طبقة إرسال حقيقية موجودة لـ SMTP/Resend/Postmark وMeta/WATI | Variables + Admin Settings |
| رفع الصور وPDF | مكتمل عبر Cloudinary، ومحليًا للتطوير | Admin → Machine → Media |
| بيانات ومخزون RGM حقيقيان | لا توجد قائمة منشورة قابلة للاستيراد من الموقع الرسمي | يدخلها الأدمن عند تسلم البيانات المعتمدة |

## 3. صفحات الموقع العام

### الصفحة الرئيسية `/` و`/ar`

تعرض تعريف RGM، زر تصفح الماكينات، البحث، آخر الماكينات المتاحة، الخدمات، وقسم بيع الماكينة. نص العنوان والمقدمة يأتيان من سجل المحتوى `home` في قاعدة البيانات، لذلك يعدله الأدمن من **Website content** دون كود. تخطيط الصفحة في `app/[[...path]]/page.tsx` داخل `section==='home'`.

### صفحة الماكينات `/machines` و`/ar/machines`

هذه هي صفحة الشوب/المخزون. بها بحث بالاسم والشركة والطراز والكود، وفلاتر للفئة والشركة وسنوات التصنيع واللون والمقاس، وترتيب النتائج. لا تظهر DRAFT أو SOLD أو ARCHIVED للعامة. شكل الفلاتر والنتائج في `catalog-view.tsx`، ومنطق النتائج الآمن في `lib/repository.ts` داخل `catalog`.

### صفحة المنتج `/machines/[slug]`

تُنشأ لكل ماكينة من slug تلقائي. تعرض الكود الدائم `RGM-M-000001`، الصور، البيانات الأساسية، المواصفات، التجهيزات، الفيديو إن وجد، PDF، السعر فقط إن سمح الأدمن، زر WhatsApp، ونموذج طلب السعر. عند تحويل حالة الماكينة إلى SOLD أو ARCHIVED تختفي من الموقع ويعالج الرابط القديم كـ 410. الواجهة في `machine-view.tsx`، والبيانات في جدول `machines` والجداول الملحقة.

### صفحات طلب الخدمة والبيع والتوريد

- `/find-a-machine`: طلب البحث عن ماكينة.
- `/sell-your-machine`: عرض ماكينة للبيع مع صور أو PDF.
- `/request-inspection`: طلب فحص.
- `/contact`: اتصال عام.
- `/services`: كل الخدمات، و`/services/[slug]` للخدمة الفردية.

كل هذه تستخدم نموذجًا موحدًا يحفظ Lead قبل أي إرسال بريد أو WhatsApp. الحقول الخاصة بكل رحلة معرفة في `InquiryForm` داخل `public-client.tsx`، والتحقق الخادمي في `lib/validation.ts`.

### المحتوى والشركة

- `/about`: صفحة الشركة من المحتوى.
- `/blog`: المقالات المهاجرة.
- `/[article-slug]`: المقال المفرد.
- `/brands` و`/brands/[brand]`: الشركات المصنعة التي لديها مخزون متاح.
- `/privacy` و`/terms`: يحتاجان نصًا قانونيًا معتمدًا قبل الإنتاج.

المقالات والصفحات المخزنة في جدول `content`. عدّلها من Admin → Website content. لا تعدّل HTML يدويًا إلا عند الحاجة، فهو ينظف قبل العرض.

### الحساب `/account`

يمكن للعميل إنشاء حساب ببريد وكلمة مرور 12 حرفًا على الأقل، ثم يؤكد بريده من رسالة Supabase. يستطيع تسجيل الدخول وتعديل الاسم واختيار تلقي النشرة والخروج. هذا الجزء لا يعمل على GitHub Pages؛ يلزم Supabase وPostgreSQL وVercel أو خادم Node.

## 4. لوحة الإدارة `/admin`

| القسم | ما تفعله |
|---|---|
| Overview | عدد الماكينات المتاحة، الاستفسارات الجديدة، استفسارات اليوم وحالات الإرسال التي تحتاج متابعة |
| Machines | إضافة وتعديل وإخفاء وأرشفة الماكينات، المواصفات، الأسعار، SEO، البيانات الداخلية والملفات |
| Leads | فتح كل استفسار، تغيير المرحلة، إسناده لموظف، إضافة ملاحظة، مشاهدة المرفقات وسجل الإرسال |
| Communications | متابعة البريد وWhatsApp، ومعالجة أو إعادة محاولة الرسائل بعد مراجعة مزود الخدمة |
| Bulk import | معاينة واستيراد CSV/XLSX وفق القالب |
| Categories and brands | إضافة وتصحيح الفئات والمصنعين |
| Website content | صفحات وخدمات ومقالات EN/AR والنشر |
| Redirects | تحويل روابط الموقع القديم مع منع الحلقات |
| Site settings | بريد وفروع وهواتف وWhatsApp وقوالب وقياس وتحكم في RESERVED |
| Staff access | ربط مستخدمي Supabase بأدوار ADMIN/SALES/MARKETING |

**الأدوار:** ADMIN يملك كل شيء بما فيه الأسعار والبيانات الداخلية. SALES يرى الماكينات والاستفسارات دون بيانات الشراء الحساسة. MARKETING يدير المحتوى والتحويلات فقط. الصلاحية مطبقة في الخادم، وليست مجرد إخفاء أزرار.

## 5. إضافة ماكينة بشكل صحيح

1. Admin → Machines → Add machine.
2. ابدأ بـ DRAFT حتى تراجع البيانات.
3. اختر الشركة والفئة، واكتب العنوانين EN وAR، الطراز، السنة، والموقع.
4. أضف المواصفات المناسبة للفئة؛ عدد الألوان لا يقبل إلا لماكينات sheetfed offset.
5. أضف السعر فقط عند توفره، ثم قرر منفصلًا عرضه للعامة أو إرساله بالبريد.
6. ارفع الصور وPDF من تبويب Media وحدد alt باللغتين.
7. راجع SEO ثم غيّر الحالة إلى AVAILABLE.

الكود ينشئ الرقم الدائم تلقائيًا عند أول حفظ ولا يعيد استخدامه حتى لو بيعت الماكينة. لا تحذف ماكينات من قاعدة البيانات؛ استخدم SOLD أو ARCHIVED.

## 6. الاستفسارات والبريد وWhatsApp

كل Lead يُحفظ مع نسخة من بيانات الماكينة في معاملة قاعدة واحدة، ثم تدخل مهام الإرسال إلى `outbox`. لذلك لا يضيع الطلب عند فشل مزود البريد. مع الإنتاج، يرسل النظام رسالة للعميل ورسالة داخلية، ثم WhatsApp فقط عند موافقة العميل وتفعيل القالب.

للتفعيل: اختر `EMAIL_PROVIDER` في `.env` وأدخل بيانات المزود، ثم اختر `WHATSAPP_PROVIDER=meta` أو `wati` وأدخل المفاتيح. راجع `docs/INTEGRATIONS_AR.md` قبل تفعيل الإرسال. لا تستخدم WhatsApp Web أو أي أتمتة غير رسمية.

## 7. النشرة البريدية

نموذج التذييل يضيف البريد كـ PENDING ثم يرسل رابط تأكيد صالح 24 ساعة. لا يصبح البريد ACTIVE قبل فتح الرابط. سجلات المشتركين في جدول `newsletter_subscribers`. قبل إرسال حملات حقيقية، أضف من لوحة الإدارة واجهة حملة أو اربط مزود mailing مخصصًا؛ لا ترسل حملات يدوية مباشرة من قاعدة البيانات.

## 8. البيانات الفعلية والبيانات التجريبية

بيانات الفروع والبريد المبدئية مأخوذة من صفحة الاتصال العامة لـRGM وهي قابلة للتعديل في Site settings. اختر رقم WhatsApp الأساسي النهائي قبل الإنتاج. الموقع الرسمي لا ينشر مخزونًا جاهزًا أو صور ماكينات يمكن ترحيلها، لذلك لا تعتمد بيانات العرض الثابتة الموجودة في GitHub Pages كمخزون فعلي. أدخل المخزون من ملفات RGM المعتمدة فقط.

## 9. التشغيل والنشر

للتطوير المحلي استخدم:

```bash
pnpm install
pnpm setup:local
pnpm dev
```

لإنتاج فعلي استخدم Vercel مع Supabase PostgreSQL وCloudinary ومزود بريد. التعليمات الدقيقة في `docs/PRODUCTION_ACTIVATION_AR.md`. أضف متغيرات البيئة في لوحة الاستضافة فقط، ولا تضع أي مفتاح في Git أو محادثة.

بعد كل تعديل محدد شغّل فقط ما يلزم:

```bash
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

## 10. طريقة طلب تعديل من Codex بأقل كوتة

اكتب الطلب بهذه الصيغة، مع رابط الصفحة والنتيجة المتوقعة فقط:

> في صفحة `/machines` عدّل نص زر البحث إلى كذا باللغتين. لا تغيّر أي ملفات خارج `lib/i18n.ts` أو مكوّن الكتالوج. شغّل typecheck وlint فقط.

أمثلة مختصرة:

- «أضف حقل وزن لماكينات الطباعة فقط، مع حفظه وعرضه في صفحة المنتج.»
- «بدّل رقم واتساب الأساسي من Site settings، ولا تعدل الهيدر يدويًا.»
- «أضف فئة Guillotine في Admin ثم اختبر إضافة ماكينة واحدة.»
- «راجع صفحة المنتج فقط على الموبايل، ولا تلمس صفحات أخرى.»

اذكر دائمًا: الصفحة أو الميزة، النص أو السلوك المطلوب، اللغة، وهل هو إنتاج أم معاينة. هذا يمنع البحث الواسع وإهدار الكوتة.

## 11. قائمة مراجعة سريعة قبل أي إطلاق

1. تأكد من `NEXT_PUBLIC_SITE_URL=https://rgmachinery.com`.
2. فعّل Confirm Email في Supabase وأضف رابط `/auth/callback`.
3. نفّذ كل SQL migrations بالترتيب.
4. أنشئ أول ADMIN في Supabase ثم جدول `staff`.
5. وثّق الدومين لدى مزود البريد وأكمل SPF/DKIM.
6. أدخل مفاتيح Cloudinary السرية في الاستضافة.
7. راجع الفروع والأرقام وخصوصية وشروط الاستخدام.
8. أدخل ماكينات وصورًا حقيقية فقط.
9. اختبر حساب عميل، استفسار، رفع ملف، بريد تأكيد، وأدمن من نطاق الإنتاج.
10. اربط DNS في Vercel بعد تأكيد الجاهزية.
